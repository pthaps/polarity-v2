# Polarity security audit and demo handoff

The security branch is local. Keep the existing RIHub deployment on its current configuration unless the preview validation below succeeds. The working branch changes API admission and article extraction behavior.

| Area | Finding and change | Remaining exposure |
| --- | --- | --- |
| API admission | Four unauthenticated routes could be called without quotas. Redis atomically enforces fixed-window per-IP limits across instances and a shared daily Gemini admission budget. The routes validate JSON objects, field types and sizes, and return bounded errors. | Public access is intentional for the demo. A caller with enough IPs can consume the shared budget and deny access until reset. Cache hits and rejected payloads reserve the same budget as other requests. Apply authenticated, per-account quotas and provider-side spending limits after the demo. |
| Article URLs | The scraper followed redirects and resolved hosts at connection time. Each hop now validates destination, rejects non-public addresses and pins the socket to a checked IP. The 12-second deadline covers all hops. HTML is capped at 2 MiB before and after decompression. | Bot-blocked and paywalled pages can fail because the Tavily extraction fallback was removed. Use the existing paste flow for accessible article text. Review a controlled extraction fallback and egress firewall after the demo. |
| Supabase | The checked-in policies gave anyone with the anonymous key unrestricted SELECT and INSERT. The SQL revokes browser-role grants and removes those policies. The metrics API publishes aggregate counts only. | Existing database permissions remain active until the reviewed SQL is applied. Inspect deployed policies and grants and confirm that only intended server paths use the privileged credential. |
| AI and cache | The model previously emitted citation URLs, retried at several layers, and used a case-folded cache key based on roughly 100 characters. The server strips citation lines, adds up to three related search results, uses a bounded cache keyed by the analysis inputs, and logs usage without source text. | Prompt injection can still influence model judgments. Search results are leads and the application does not test whether they substantiate a claim. Cached successful analyses are per-instance. Usage estimates based on configured prices can differ from invoices. |
| Browser and extension | Restricted outbound links, removed wildcard CORS, added browser security headers and narrowed active extension host access to its configured HTTPS site plus loopback development hosts. | Installed extension users may need to reopen Options and save the API origin to grant access again. Browser permissions remain device-local. |
| Dependencies | Moved Next.js from 14.2.18 to 14.2.35 within the existing release line. | The production dependency audit still reports known issues. Next.js 14 is unsupported. Plan a supported-version upgrade and review the transitive advisories before deploying beyond the demo. |

## Preview and rollout

1. Configure `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` in the preview's server environment. Production returns HTTP 503 when Redis is missing or unavailable. A local development server can run with an in-process limiter. Use a dedicated Redis deployment or isolate demo traffic if sharing quotas across previews is undesirable.
2. The current limits per Vercel client IP per minute are 6 for analyze, 20 for fetch-news, 10 for extension-analyze and 6 for feedback. Missing Vercel IP information uses a shared client bucket. The shared UTC-day Gemini budget reserves eight possible attempts for web analysis and two for extension-analyze, out of 800. Each admitted web analysis can make up to three basic Tavily searches. The shared daily caps for fetch-news and feedback are 3,000 and 600 requests. Set plan-specific rates from `.env.example` to include estimated USD in structured provider logs.
3. Confirm the preview with one public article, one paste analysis, extension Options and full-report handoff, and feedback persistence. Confirm HTTP 429 and `Retry-After` using non-billable invalid requests against a preview Redis instance. Check the log stream for usage metrics without article content or secrets.
4. After the demo, configure `SUPABASE_SERVICE_ROLE_KEY` server-side and verify the application methods against a staging database. The legacy `SUPABASE_KEY` fallback is for existing deployments. Review `frontend/supabase-migration.sql` before executing it. Validate anonymous SELECT/INSERT denial and server insert and metrics access before changing production. No production database change was executed in this audit.

## Automated checks

From `frontend`, run `npm test`, `npx tsc --noEmit`, `npm run lint`, and `npm run build`. The tests use fixtures for Redis, Gemini and Tavily. They cover the website URL and paste workflows, the extension route and background worker, and a real local socket test for DNS pinning.
